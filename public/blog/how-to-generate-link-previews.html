How to Generate Link Previews Like Slack and Discord

When you paste a URL into Slack, Discord, or iMessage, it expands into a rich card with a title, image, and description. Here's how that works under the hood — and how to add it to your own app without reinventing the hard parts.

That little preview card is one of the highest-trust UI elements you can add to a chat app, comment box, CMS, or bookmarking tool. A bare URL looks like spam; an unfurled link with a title and thumbnail looks legitimate and gets clicked. This guide explains exactly how those previews are generated and the cleanest way to build them.

What a link preview actually is

A "link preview" (or "unfurl") is built from metadata tags in the linked page's HTML <head>. The dominant standard is the Open Graph protocol, originally from Facebook and now read by virtually every platform. A typical page exposes:

<meta property="og:title"       content="The Verge" />
<meta property="og:description" content="Technology, science and culture." />
<meta property="og:image"       content="https://.../cover.png" />
<meta property="og:site_name"   content="The Verge" />

To build a preview, you fetch the page, read those tags, and render a card. Simple in theory. The trouble is everything that happens between "fetch the page" and "read those tags."

The hard part: why a 10-line scraper isn't enough

Most developers start with a quick fetch() + regex, ship it, and then spend the next month patching the long tail of pages that break it. The real-world edge cases:

  • Redirects. Short links (t.co, bit.ly) and http → https hops mean the URL you were given isn't the page you end up parsing. You have to follow them — safely.
  • Missing Open Graph tags. Plenty of sites have no og:* tags at all. You need a fallback chain: Open Graph → Twitter Card → standard <title> and meta description → first <h1>/<img>.
  • Relative image URLs. og:image is often /images/cover.png, not a full URL. You must resolve it against the final page URL or the image won't load.
  • Encodings & entities. Non-UTF-8 pages and HTML entities turn into mojibake if you don't decode them.
  • Timeouts & huge pages. A slow or multi-megabyte page can hang your request or blow up memory. You need a hard timeout and a byte cap.
  • Bot blocking. Some sites serve different markup to non-browser user agents, or block them entirely.
  • SSRF (the dangerous one). If you let users submit URLs and fetch them server-side, an attacker can point you at http://169.254.169.254 (cloud metadata) or http://localhost to reach internal services. You must block private, loopback, and link-local addresses — on every redirect hop.
The SSRF point is not optional. A link-preview feature that fetches arbitrary user-supplied URLs is one of the most common SSRF vectors in real applications. If you build this yourself, validate the resolved IP of every hop against private ranges before connecting.

The easy way: one API call

Instead of owning all of that, you can hand the URL to a service that has already solved the edge cases and get clean JSON back. Here's the same result in three languages using the Link Preview API:

cURL

curl "https://link-preview14.p.rapidapi.com/preview?url=https://www.theverge.com" \
  -H "X-RapidAPI-Key: YOUR_KEY" \
  -H "X-RapidAPI-Host: link-preview14.p.rapidapi.com"

JavaScript

const res = await fetch(
  "https://link-preview14.p.rapidapi.com/preview?url=" +
    encodeURIComponent(targetUrl),
  { headers: {
      "X-RapidAPI-Key": "YOUR_KEY",
      "X-RapidAPI-Host": "link-preview14.p.rapidapi.com",
  } },
);
const preview = await res.json();

Python

import requests
r = requests.get(
    "https://link-preview14.p.rapidapi.com/preview",
    params={"url": target_url},
    headers={
        "X-RapidAPI-Key": "YOUR_KEY",
        "X-RapidAPI-Host": "link-preview14.p.rapidapi.com",
    },
)
preview = r.json()

Frequently asked questions

What is a link preview?

The rich card apps show when you paste a URL — title, description, image, and site name — generated from the Open Graph and other metadata tags in the page's HTML.

How do I get the title, description, and image from a URL?

Fetch the page and parse its og:title, og:description, and og:image tags, with fallbacks to Twitter Card and standard meta tags. You also have to handle redirects, encodings, missing fields, timeouts, and security — which is why a dedicated API is usually faster than building it yourself.

Why not just scrape the Open Graph tags myself?

You can, and for a single trusted URL it's fine. It gets hard when URLs are user-submitted: you need safe redirect following, size/time caps, relative-URL resolution, graceful fallbacks, and SSRF blocking on every hop. Those are exactly the cases a purpose-built service handles.
